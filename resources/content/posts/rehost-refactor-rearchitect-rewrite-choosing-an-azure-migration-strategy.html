Cloud migration conversations often collapse four very different decisions into one word: migration. In Azure architecture work—especially the kind covered by AZ-305—the important question is not simply whether a workload can move. It is what must change, what must remain stable, and what evidence will tell us that the change worked.

Four strategies provide a useful vocabulary: rehost, refactor, re-architect, and rewrite. They are not a ladder where rewrite is automatically the most mature answer. They are different levels of intervention, risk, and expected benefit.

Start with the workload, not the preferred technology

AZ-305 encourages architects to reason from business and technical requirements: reliability, security, performance, operations, cost, and time to value. Those requirements should drive the migration strategy. A team that begins with “we need Kubernetes” or “we should rewrite this in .NET” has already skipped the architectural decision.

Before choosing a path, establish a baseline:

  • What business capability does the workload provide?
  • What are its dependencies, data flows, identity requirements, and failure modes?
  • Which quality attributes are failing today, and which are already acceptable?
  • What downtime, data-loss, compliance, and rollback constraints apply?
  • How will we prove that the migrated workload is equivalent or better?

That last question is the one teams neglect most often. A successful deployment is not the same thing as a successful migration. We need an observable acceptance contract: representative requests, data checks, performance expectations, security controls, operational signals, and a rollback procedure.

Rehost: move the workload with minimal change

Rehosting, often called “lift and shift,” moves the workload to Azure while preserving most of its application and runtime design. An on-premises virtual machine may move to Azure Virtual Machines. A database may move to a compatible managed or hosted database with few application changes.

Rehost when the main objective is speed, datacenter exit, capacity, or a low-risk first step. It is often the right answer when the application is stable, the migration deadline is real, and the organization needs to establish a cloud landing zone before pursuing deeper modernization.

Rehosting is not free of architecture work. The surrounding platform still needs deliberate design:

  • Place workloads in the correct subscription, resource group, region, and network boundary.
  • Use managed identity, RBAC, private connectivity, encryption, backup, and monitoring where appropriate.
  • Define availability and disaster-recovery expectations rather than assuming Azure makes them automatic.
  • Measure cost after migration; an oversized virtual machine is still oversized in Azure.

The main risk is preserving an operational problem while changing its hosting location. Rehost is a valid strategy when that tradeoff is explicit. It becomes a mistake when “minimal application change” is confused with “no design required.”

Refactor: change the implementation without changing the product

Refactoring changes the internals of the application while preserving its externally visible behavior. The goal is usually to improve maintainability, testability, deployment, or operational efficiency without changing the business capability itself.

Examples include:

  • Breaking a monolith into clearer modules while keeping one deployable application.
  • Replacing local file storage with Azure Blob Storage behind the same application interface.
  • Moving configuration and secrets out of code and into managed services.
  • Adding health checks, structured logging, telemetry, automated tests, and repeatable deployment.
  • Replacing a self-managed database component with an Azure-managed equivalent while preserving the data model.

Refactoring is a strong choice when the application is valuable but its current structure makes reliable delivery difficult. It can reduce technical friction without taking on the full domain and integration risk of a new architecture.

The discipline is to keep the boundary honest. If the team changes the data model, communication patterns, consistency model, or user-facing behavior, the work may have crossed into re-architecture. That is not bad, but it should be named and planned as such.

Re-architect: change the structure to meet new requirements

Re-architecting changes the system’s fundamental architecture so it can meet requirements the current design cannot satisfy. The motivation is usually a quality attribute: elastic scale, regional resilience, stronger isolation, lower latency, independent deployment, or a new integration model.

A re-architecture might introduce asynchronous messaging, separate read and write models, independently scalable services, event-driven processing, containers, or a different data-partitioning strategy. Azure services can support these designs, but the service list is not the architecture. The architecture is the set of responsibilities, boundaries, dependencies, and guarantees.

Re-architecting deserves a staged migration plan:

  1. Define the target capabilities and the constraints that justify the change.
  2. Choose a seam between the existing system and the new components.
  3. Move one slice of behavior or data at a time.
  4. Run old and new paths with controlled comparison where necessary.
  5. Measure the target quality attributes before retiring the old path.

This is where evolutionary architecture matters. Architecture should be allowed to improve incrementally, with fitness functions that detect drift. Useful fitness functions might measure deployment frequency, error rate, recovery time, policy compliance, data freshness, or cost per workload. They turn architectural intent into something the delivery system can repeatedly check.

Rewrite: replace the system deliberately

Rewriting builds a replacement rather than adapting the existing implementation. It may be justified when the current code is effectively unmaintainable, the platform is obsolete, the licensing model is untenable, or the business needs are different enough that preserving the old design creates more risk than starting over.

Rewrite is the strategy with the largest apparent freedom and the largest hidden risk. The existing system contains undocumented behavior, edge cases, data assumptions, operational workarounds, and user knowledge. A rewrite removes the implementation, but it does not remove those responsibilities.

A rewrite should therefore begin with discovery and characterization, not an empty repository:

  • Record actual workflows and important exception paths.
  • Inventory integrations, scheduled jobs, reports, exports, and identity flows.
  • Capture representative data and define migration and reconciliation rules.
  • Build contract, acceptance, and performance tests around behavior that matters.
  • Define coexistence, cutover, rollback, and support plans before the replacement is complete.

“We will know what the old application did when we replace it” is not a migration strategy. It is a discovery plan with an alarming production date.

The strategy can change by component

A real portfolio rarely has one migration strategy. The application tier may be refactored, the database rehosted temporarily, a reporting subsystem re-architected, and a small obsolete utility rewritten. Treating the whole workload as one indivisible unit forces an unnecessarily expensive decision.

Map the system by capability and dependency. For each component, record the selected strategy, the reason, the target Azure service or runtime, the owner, the acceptance checks, and the rollback path. This makes the migration reviewable instead of turning it into a slogan.

Source of truth and delivery evidence

Migration work also needs a delivery architecture. Infrastructure, application configuration, policies, and target inventories should have explicit sources of truth. A local note, a cloud portal setting, and a generated artifact are not interchangeable.

A reliable migration path should make these facts visible:

  • Which source revision produced the candidate.
  • Which tests and acceptance checks passed.
  • Which exact package or artifact was deployed.
  • Which identity performed the operation and what it was allowed to change.
  • Which live checks confirmed the result.
  • What can be redeployed if the cutover fails.

Build once, retain the exact tested bytes, and promote those bytes rather than rebuilding at every stage. Keep application publication separate from infrastructure reconciliation. Keep deployment credentials separate from runtime identities. These are not bureaucratic details; they are how an architect preserves causality when a migration behaves unexpectedly.

My default recommendation

When the evidence is incomplete, start with the smallest reversible move that creates better evidence. That may be a rehost into a properly governed landing zone, followed by refactoring behind stable interfaces. If the workload has a clear architectural constraint, introduce a seam and re-architect one capability at a time. Reserve a rewrite for a case where discovery, behavior coverage, data migration, coexistence, and rollback are all funded parts of the work.

The best AZ-305 answer is rarely the most fashionable Azure service or the most ambitious modernization plan. It is the strategy that matches the requirement, makes risk explicit, preserves a way back, and produces evidence that the new architecture is actually better.
